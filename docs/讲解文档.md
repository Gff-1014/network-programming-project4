## 一、先看全局

### 1.1 一句话定位

这是一个桌面版多人大厅与斗地主聊天室：

- 服务端使用 `asyncio.start_server` 管理多条 TCP 连接；
- 每条 TCP 消息使用“4 字节大端长度前缀 + UTF-8 JSON”；
- `Hub` 保存账号、房间、在线会话和重连预约；
- `Room` 负责房间隔离和广播；
- `Table` 把斗地主状态机接入网络，所有出牌结果由服务端裁决；
- 客户端是 Tkinter 桌面程序，支持聊天、私聊、群聊、牌桌和观战。

### 1.2 一条消息的完整路径

讲解任何功能时，都可以先把它放回下面这条链路：

```text
客户端界面
  -> ClientSession
  -> Connection.send
  -> encode_frame：长度头 + JSON
  -> TCP
  -> 服务端 read_frame
  -> Session.run / _dispatch
  -> @register 注册的处理器
  -> Hub / Room / Table
  -> Session.send：进入该连接的发送队列
  -> Session._writer_loop
  -> 客户端 Connection._pump
  -> ClientSession._handle
  -> 界面事件
```

这条链路对应四类核心问题：

1. 字节流怎样还原成消息：分帧；
2. 多个连接怎样互不阻塞：异步会话和每连接发送队列；
3. 共享状态怎样保持一致：`Hub`、`Room`、`Table`；
4. 业务动作怎样不被客户端伪造：服务端状态机和规则引擎统一裁决。

### P0-1 TCP 分帧：把字节流还原为消息

**对应要求**

- TCP 消息必须带长度或等价边界字段；

- [server/framing.py:42](C:/Users/guofei/Documents/ChatGPT/网络编程/网络编程项目4/server/framing.py:42)：长度为 0、超过上限、非法 JSON、非法 UTF-8 的拒绝逻辑。

**讲解要点**

1. TCP 是连续字节流，不保留“消息边界”。如果客户端一次发送两条 JSON，服务端可能一次读到两条；如果一次只到半条，服务端也可能只读到前半段。
2. 本项目先读固定 4 字节，得到消息体长度 `N`，再用 `readexactly(N)` 读完整消息体。这样粘包会被拆开，半包会等待剩余字节。
3. `>I` 表示大端无符号 32 位整数，发送端和接收端必须使用相同字节序。
4. 长度超限时，消息体没有继续读取，字节流已经发生错位，因此 `fatal=True`，不能假装还能继续解析。
5. 非法 JSON、非法 UTF-8、非对象载荷属于内容错误，返回 `BAD_FRAME`；连续多次错误由会话层决定是否断开。

**可能追问**

- 为什么不用换行符分帧？JSON 文本可以包含换行，而且二进制安全性和长度控制不如长度前缀明确。
- 为什么长度头也要用 `readexactly`？因为 TCP 不保证一次就能给你 4 字节。

**讲解要点**

1. 广播是“投递到每个人的队列”，不是在一个全局 `send()` 中逐个等待网络写完。
2. 慢客户端只会卡住自己的 `_writer_loop()`，其他连接仍然可以入队和写出。

## 七、答辩时主动说明的边界

1. **客户端自动重连**：服务端有 token 重连和 60 秒预约，但桌面客户端没有完整的断线自动重连管理器；演示时应说明这是已知待完善项。
2. **密码存储**：当前为课程演示的预置账号和内存账号表，密码没有做生产级哈希存储。
3. **私信历史**：只保存在服务端内存，服务端重启后会清空。
4. **跨机运行**：服务端可以通过 `DDZ_HOST=0.0.0.0` 监听局域网地址，但仍需处理防火墙、地址配置和真实跨机测试；当前重点验证是本机多进程。
5. **界面美化**：`client/ui_ctk.py` 是独立的现代皮肤层，`--ui classic` 可以回退；界面不是网络核心评分点。

这些边界主动说明，比把项目描述成生产级系统更稳妥；核心网络机制和测试证据才是讲解重点。
